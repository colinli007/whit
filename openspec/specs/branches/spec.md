# branches Specification

## Purpose

在 Whit 中完成 VS Code 源代码管理的分支操作：签出、创建、重命名、删除、合并、变基、发布分支，以及合并 / 变基进行中的继续与中止。交互、文案和 git 行为都参照 VS Code 1.117 的默认设置。

## Requirements

### Requirement: 签出到

点击状态栏的分支名（包括分离头指针时显示的短哈希），或选择「…」菜单的「签出到...」，SHALL 打开快速选择框，占位文字为「选择要签出的分支或标记」。列表内容：

- 三个始终显示的操作条目：「创建新分支...」「创建新分支依据...」「签出已分离…」。
- 「分支」组：全部本地分支（包括当前分支）。
- 「远程分支」组：全部远程跟踪分支，不包括 `<远程>/HEAD`。
- 「标记」组：全部标记。

每组内按最后一次提交的时间从新到旧排列。本地分支与上游有差异（或上游已被删除，此时为 `0↓ 0↑`）时，说明为「落后数↓ 领先数↑ • 相对时间」，没有上游或与上游一致时只显示相对时间（与 VS Code 相同）；远程分支和标记的说明为相对时间。详情为「作者 • 7 位短哈希 • 提交标题」。相对时间用中文，如「刚刚」「3 分钟前」「14 小时前」「2 天前」「1 周前」「3 个月前」「1 年前」。输入框为空时操作条目排在最前；输入了文字时，匹配的引用排在前面，之后是一条分隔线，再之后是操作条目。

确认后：
- 本地分支：签出该分支。
- 远程分支 `<远程>/<名称>`：如果已有本地分支以它为上游，签出那个本地分支；否则新建一个跟踪它的同名本地分支并签出。
- 标记：以分离头指针的方式签出标记所指的提交。

签出完成后 SHALL 刷新改动列表、状态栏分支名和同步计数，提交信息输入框的占位文字随之更新为新分支名。

#### Scenario: 切换到另一个本地分支

- **WHEN** 当前在 `main-next`，工作区干净，用户点击状态栏分支名并选择 `test`
- **THEN** 仓库切换到 `test`，状态栏显示 `test`，输入框占位文字变为 `消息(⌘Enter 在"test"提交)`

#### Scenario: 签出没有本地分支的远程分支

- **WHEN** 存在 `origin/feature`，本地没有跟踪它的分支，用户选择 `origin/feature`
- **THEN** 新建本地分支 `feature` 跟踪 `origin/feature` 并签出，状态栏显示 `feature` 和 `0↓ 0↑`

#### Scenario: 签出已有本地跟踪分支的远程分支

- **WHEN** 本地分支 `dev` 的上游是 `origin/dev`，用户选择 `origin/dev`
- **THEN** 签出本地分支 `dev`，不新建分支

### Requirement: 工作区有改动时签出

签出因为本地改动会被覆盖而失败时，系统 SHALL 弹出确认框「签出会覆盖本地更改。」，按钮依次为「储藏并签出」「迁移更改」「强制签出」「取消」：

- 储藏并签出：把全部改动（包括未跟踪文件）储藏起来，然后签出。
- 迁移更改：储藏全部改动、签出，然后弹出刚才的储藏，把改动带到新分支；弹出时发生冲突则提示失败，冲突文件出现在「合并更改」组。
- 强制签出：放弃全部改动（未跟踪文件被删除），然后签出。
- 取消：不做任何修改。

签出因其它原因失败时 SHALL 按一般写操作失败处理（弹出带 git 输出的通知）。

#### Scenario: 迁移更改

- **WHEN** 当前在 `main`，`a.rs` 有未提交的修改且会被签出覆盖，用户签出 `dev` 并选择「迁移更改」
- **THEN** 仓库切换到 `dev`，`a.rs` 的修改仍在「更改」组中

#### Scenario: 强制签出

- **WHEN** 同上，用户选择「强制签出」
- **THEN** `a.rs` 的修改和所有未跟踪文件被丢弃，仓库切换到 `dev`

#### Scenario: 不冲突的改动直接带过去

- **WHEN** `b.rs` 有修改，但 `main` 和 `dev` 中的 `b.rs` 内容相同
- **THEN** 签出 `dev` 直接成功、不弹确认框，`b.rs` 的修改保留

### Requirement: 创建新分支

选择「创建新分支...」时：如果快速选择框里已经输入了文字，SHALL 直接把这段文字规范化后作为分支名；否则 SHALL 打开输入框，占位文字「分支名称」，提示「请提供新的分支名称」。选择「创建新分支依据...」时，SHALL 先打开快速选择框「选择一个 ref 以从中创建分支」，列出 `HEAD`（说明为当前提交的短哈希）、本地分支、远程分支和标记，选好起点后再按同样规则取得分支名。

分支名规范化：去掉首尾空白和开头的 `-`，把空白以及 git 不允许的字符（`~ ^ : \ * [` 等、`..`、结尾的 `.`、`/` 或 `.lock`）替换为 `-`。输入框校验：规范化后与已有本地分支重名时显示错误「分支“x”已存在」且不接受回车；规范化结果与输入不同时显示提示「新分支将为“x”」。

确认后 SHALL 从起点（默认当前 `HEAD`）创建分支并签出，新分支不设置上游。

#### Scenario: 在签出列表中直接输入名字

- **WHEN** 用户打开签出列表，输入 `feature/login`，选择「创建新分支...」
- **THEN** 不再弹输入框，直接创建并签出 `feature/login`，状态栏显示「发布分支」

#### Scenario: 从远程分支创建

- **WHEN** 用户选择「创建新分支依据...」，选 `origin/dev`，输入 `hotfix`
- **THEN** 新建 `hotfix` 指向 `origin/dev` 的提交并签出，`hotfix` 没有上游

### Requirement: 签出已分离

选择「签出已分离…」时 SHALL 打开快速选择框「选择要在分离模式下签出的分支」，列出本地分支和远程分支（不含标记，也不含创建分支的操作条目）。确认后 SHALL 以分离头指针的方式签出该分支当前的提交，状态栏显示该提交的短哈希。

#### Scenario: 分离签出

- **WHEN** 用户选择「签出已分离…」再选 `main`，`main` 指向 `05c648e…`
- **THEN** 仓库处于分离头指针状态，状态栏显示 `05c648e`

### Requirement: 重命名分支

「分支」子菜单的「重命名分支...」SHALL 打开输入框，初始值为当前分支名，校验规则同创建分支。确认后 SHALL 把当前分支改为新名字；分支名无效时提示「分支名称无效」，重名时提示「已存在名为“x”的分支」。处于分离头指针状态时该菜单项 SHALL 不可用。

#### Scenario: 重命名

- **WHEN** 当前分支 `feat`，用户重命名为 `feature`
- **THEN** 状态栏显示 `feature`，`feat` 不再存在

### Requirement: 删除分支

「删除分支...」SHALL 打开快速选择框「选择要删除的分支」，列出除当前分支外的本地分支。确认后删除该分支；分支没有完全合并时，SHALL 弹出确认框「“x”分支未被完全合并。是否仍要删除?」，选择「删除分支」才强制删除，否则不删除。

「删除远程分支...」SHALL 打开快速选择框「选择要删除的远程分支」，列出除当前分支上游外的远程分支。确认后 SHALL 在远程上删除该分支（远程操作，按远程认证规则执行），不再额外确认（与 VS Code 一致）。

#### Scenario: 删除未合并的分支

- **WHEN** 分支 `spike` 有未合并到当前分支的提交，用户删除 `spike`
- **THEN** 系统询问是否仍要删除；选「删除分支」后 `spike` 被删除，取消则保留

#### Scenario: 删除远程分支

- **WHEN** 用户选择删除远程分支 `origin/old`
- **THEN** 远程上的 `old` 分支被删除，`origin/old` 不再出现在签出列表中

### Requirement: 合并

「合并...」SHALL 打开快速选择框「选择要合并的分支或标记」，列出本地分支、远程分支、标记，不包括当前分支和它的上游。确认后 SHALL 把所选引用合并到当前分支（遵循用户自己的 git 合并配置）。发生冲突时 SHALL 弹出警告通知「存在合并冲突。请在提交之前解决这些冲突。」，冲突文件出现在「合并更改」组。

#### Scenario: 无冲突合并

- **WHEN** 当前在 `main`，用户合并 `feature`，没有冲突
- **THEN** 产生合并结果，状态栏的领先数相应增加

#### Scenario: 合并冲突

- **WHEN** `main` 和 `feature` 修改了 `a.rs` 的同一行，用户合并 `feature`
- **THEN** 弹出合并冲突的警告，`a.rs` 出现在「合并更改」组，操作按钮显示「继续」

### Requirement: 变基

「变基分支…」SHALL 打开快速选择框「选择要变基到的分支」，列出本地分支和远程分支，不包括当前分支；当前分支有上游时，上游 SHALL 排在列表第一位，说明为「(upstream)」，且不在分组中重复出现。确认后 SHALL 把当前分支变基到所选分支。发生冲突时提示同合并冲突，冲突文件出现在「合并更改」组。

#### Scenario: 变基到上游

- **WHEN** 当前分支 `main` 的上游为 `origin/main`，用户打开「变基分支…」
- **THEN** 列表第一项是 `origin/main`，说明「(upstream)」

### Requirement: 合并或变基进行中

仓库处于合并进行中（存在未完成的合并）或变基进行中时：

- 提交框下方的操作按钮 SHALL 显示「继续」（带 ✓ 图标）。还有未解决冲突（「合并更改」组不为空）时按钮不可用；冲突都已暂存后可用。
- 合并进行中：提交信息输入框为空时 SHALL 预填 git 生成的合并提交信息；点击「继续」等同于提交，完成合并。
- 变基进行中：点击「继续」SHALL 继续变基（沿用 git 为当前提交准备的提交信息，不打开编辑器）；后续提交再出现冲突时，冲突文件重新出现在「合并更改」组。
- 「…」菜单「提交」子菜单 SHALL 在变基进行中显示「中止变基」；「分支」子菜单 SHALL 在合并进行中显示「中止合并」。中止后仓库回到合并或变基开始前的状态。

#### Scenario: 解决冲突后继续合并

- **WHEN** 合并 `feature` 产生冲突，用户在外部解决 `a.rs` 后点它行上的 + 暂存
- **THEN** 「合并更改」组为空，输入框里是 `Merge branch 'feature'`，「继续」可用；点击后合并完成，按钮恢复为「提交」或「同步更改」

#### Scenario: 中止变基

- **WHEN** 变基产生冲突，用户选择「…」→「提交」→「中止变基」
- **THEN** 当前分支回到变基前的提交，「合并更改」组消失

### Requirement: 发布分支

发布分支（「分支」子菜单的「发布分支...」、状态栏的「发布分支」、提交框下方的「发布分支」按钮）SHALL 把当前分支推送到远程并设为上游：仓库只有一个远程时直接使用它；有多个远程时 SHALL 打开快速选择框「选取要将分支“x”发布到的远程:」，每项为远程名，说明为推送地址；没有任何远程时 SHALL 提示「仓库未配置任何要发布到的远程仓库。」。

#### Scenario: 多个远程

- **WHEN** 仓库有 `origin` 和 `upstream` 两个远程，当前分支 `feature` 没有上游，用户点击「发布分支」
- **THEN** 快速选择框列出 `origin` 和 `upstream`；选 `upstream` 后 `feature` 被推送并以 `upstream/feature` 为上游

### Requirement: 分支操作的执行与反馈

本能力中所有改动仓库的操作 SHALL 遵循已有「写操作的执行与反馈」规则：后台执行、同一时间只执行一个、执行期间相关入口不可用、失败时弹出带 git 输出的通知、结束后自动刷新。快速选择框或输入框中途取消时 SHALL 不对仓库做任何修改。签出、合并、变基、强制签出 SHALL 只在用户确认对应条目或按钮后执行。

#### Scenario: 操作进行中再次签出

- **WHEN** 推送正在进行，用户点击状态栏分支名
- **THEN** 不打开签出列表（分支名不可点击），推送结束后恢复可点击
